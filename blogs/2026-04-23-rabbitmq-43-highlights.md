<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="open-source-rabbitmq">Open-Source RabbitMQ<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#open-source-rabbitmq" title="Direct link to Open-Source RabbitMQ">​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="quorum-queue-features">Quorum Queue Features<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#quorum-queue-features" title="Direct link to Quorum Queue Features">​</a></h3>
<p><a class="" href="https://www.rabbitmq.com/docs/quorum-queues">Quorum queues</a> were introduced seven years ago in RabbitMQ 3.8.
They are the recommended queue type for data safety, durably persisting messages to disk and replicating them across RabbitMQ nodes.</p>
<p>Built on the Raft consensus algorithm, quorum queues implement a replicated state machine.
This ensures data consistency during network faults, maintaining availability as long as a majority of the queue members remain online.</p>
<p>Almost every minor release has brought enhancements to quorum queues, and RabbitMQ 4.3 is no exception, delivering significant new features.</p>
<h4 class="anchor anchorTargetStickyNavbar_Vzrq" id="32-message-priorities">Support for 32 Strict Message Priority Levels<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#32-message-priorities" title="Direct link to Support for 32 Strict Message Priority Levels">​</a></h4>
<p>Prior to RabbitMQ 4.0, quorum queues did not support message priorities.</p>
<p>RabbitMQ 4.0 through 4.2 supported <a class="" href="https://www.rabbitmq.com/blog/2024/08/28/quorum-queues-in-4.0#message-priorities">two relative priority levels</a>: normal and high.
If a queue contained both, consumers received a mix at a ratio of two high-priority messages for every one normal-priority message.</p>
<p>RabbitMQ 4.3 introduces support for 32 strict priority levels. Messages with a higher priority are now delivered to consumers strictly before those with a lower priority.</p>
<p>As highlighted by the orange rectangle below, the Management UI now displays per-priority message counts for each quorum queue, allowing operators to monitor queue depth by priority level:</p>
<p></p><figure><img alt="Management UI - Quorum Queue Details" class="img_ev3q" height="2438" src="https://www.rabbitmq.com/assets/images/qq-details-cab48b50d277a7c058ccd26d1a891056.png" width="4040" /><figcaption>Management UI - Quorum Queue Details</figcaption></figure><p></p>
<p>The red rectangles highlight the new Delayed Retries feature, which we cover next.</p>
<h4 class="anchor anchorTargetStickyNavbar_Vzrq" id="delayed-retries">Delayed Retries<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#delayed-retries" title="Direct link to Delayed Retries">​</a></h4>
<p>Delayed retries are essential when specific messages cannot be processed due to transient failures. Common examples include:</p>
<ul>
<li class=""><strong>Entity-Specific Rate Limits:</strong> An API might rate-limit requests for a specific user ID while allowing requests for others.</li>
<li class=""><strong>Database Locks:</strong> A single row in your database might be temporarily locked. Pausing the entire consumer would prevent you from updating thousands of other unlocked rows.</li>
</ul>

Once the database is restored, you can resume the consumer.</p></div></div>
<p>Before RabbitMQ 4.3, implementing delayed retries required one of two complex workarounds:</p>
<ol>
<li class="">
<p><strong>Dead-letter cycles</strong>:
Consumers could reject the message, routing it to a <a class="" href="https://www.rabbitmq.com/docs/dlx">dead-letter queue</a>.
This queue would have a <a class="" href="https://www.rabbitmq.com/docs/ttl">message-TTL</a> configured, after which the message was dead-lettered back to the original queue:</p>
<div class="language-text codeBlockContainer_Ckt0 theme-code-block"><div class="codeBlockContent_QJqH"><pre class="prism-code language-text codeBlock_bY9V thin-scrollbar" style="color: #393A34; background-color: #f6f8fa;" tabindex="0"><code class="codeBlockLines_e6Vv"><div class="token-line" style="color: #393A34;"><span class="token plain">  +-------------------+    1) Consume        +----------+</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  |  Original Queue   | -------------------&gt; | Consumer |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  +-------------------+ &lt;------------------- +----------+</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">    |                ^      2) Reject</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">    |                |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">    |                |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">    | 3) Dead-letter | 4) Dead-letter after TTL</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">    |                |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">    v                |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  +-------------------+</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  | Dead-letter Queue |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  |    (with TTL)     |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  +-------------------+</span><br /></div></code></pre></div></div>
<p>The downside is that RabbitMQ must rewrite the message twice. Furthermore, the default at-most-once dead-letter strategy risks message loss, while <a class="" href="https://www.rabbitmq.com/blog/2022/03/29/at-least-once-dead-lettering">at-least-once dead-lettering</a> introduces its own <a class="" href="https://www.rabbitmq.com/blog/2022/03/29/at-least-once-dead-lettering#caveats">caveats</a>.</p>
</li>
<li class="">
<p><strong>Re-publishing to a message scheduler</strong>:
Alternatively, consumers could re-publish the failed message to a <a class="" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#message-scheduler">message scheduler</a>.</p>
<div class="language-text codeBlockContainer_Ckt0 theme-code-block"><div class="codeBlockContent_QJqH"><pre class="prism-code language-text codeBlock_bY9V thin-scrollbar" style="color: #393A34; background-color: #f6f8fa;" tabindex="0"><code class="codeBlockLines_e6Vv"><div class="token-line" style="color: #393A34;"><span class="token plain">  +-------------------+    1) Consume        +----------+</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  |  Original Queue   | -------------------&gt; | Consumer |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  +-------------------+ &lt;------------------- +----------+</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">          ^                 3) Acknowledge     |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">          |                                    |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">          | 4) Publish after delay             | 2) Re-publish new message with delay</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">          |                                    |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">          |                                    |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  +-------------------+                        |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  | Message Scheduler | &lt;----------------------+</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  +-------------------+</span><br /></div></code></pre></div></div>
<p>This also forces the message to be rewritten. Additionally, if a network failure occurs between the client and RabbitMQ <em>after</em> the re-publish but <em>before</em> the acknowledgement, the message is both re-published and re-queued. This creates duplicates: one copy in the scheduler and another in the original queue.</p>
</li>
</ol>
<p>RabbitMQ 4.3 introduces a much cleaner solution:
The quorum queue simply sets the delayed message aside internally, making it available for redelivery (to any consumer) only after the configured delay elapses.</p>
<div class="language-text codeBlockContainer_Ckt0 theme-code-block"><div class="codeBlockContent_QJqH"><pre class="prism-code language-text codeBlock_bY9V thin-scrollbar" style="color: #393A34; background-color: #f6f8fa;" tabindex="0"><code class="codeBlockLines_e6Vv"><div class="token-line" style="color: #393A34;"><span class="token plain">  +--------------------------------+</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  |          Quorum Queue          |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  |                                |     1) Consume       +----------+</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  |  [Message set aside until      | -------------------&gt; | Consumer |</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  |   configured delay elapses]    | &lt;------------------- +----------+</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  |                                |     2) Return</span><br /></div><div class="token-line" style="color: #393A34;"><span class="token plain">  +--------------------------------+</span><br /></div></code></pre></div></div>
<p>The key benefits include:</p>
<ul>
<li class=""><strong>Improved Performance:</strong> Messages are not rewritten, lowering broker resource overhead.</li>
<li class=""><strong>Simpler &amp; Safer Semantics:</strong> Eliminates the risk of message loss or duplication.</li>
<li class=""><strong>Granular Control:</strong> Delays can be configured per queue or per message.</li>
</ul>
<p>To configure delayed retries, use the following queue arguments or policies:</p>
<ul>
<li class=""><code>x-delayed-retry-type</code> (queue argument) or <code>delayed-retry-type</code> (<a class="" href="https://www.rabbitmq.com/docs/policies">policy</a>): Defines the conditions for delaying a message. Options are <code>disabled</code> (default), <code>all</code>, <code>returned</code>, or <code>failed</code>. (See the <a class="" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#unlimited-returns">Unlimited Returns</a> table below for the difference between <code>returned</code> and <code>failed</code>).</li>
<li class=""><code>x-delayed-retry-min</code> / <code>delayed-retry-min</code>: The minimum delay time in milliseconds.</li>
<li class=""><code>x-delayed-retry-max</code> / <code>delayed-retry-max</code>: The maximum delay time in milliseconds (defaults <code>delayed-retry-min</code>).</li>
</ul>
<p>The delay is calculated using linear backoff based on the message's <code>delivery-count</code>:</p>
<div class="language-text codeBlockContainer_Ckt0 theme-code-block"><div class="codeBlockContent_QJqH"><pre class="prism-code language-text codeBlock_bY9V thin-scrollbar" style="color: #393A34; background-color: #f6f8fa;" tabindex="0"><code class="codeBlockLines_e6Vv"><div class="token-line" style="color: #393A34;"><span class="token plain">min(delayed-retry-min * delivery-count, delayed-retry-max)</span><br /></div></code></pre></div></div>
<p>Consequently, a message's delay increases the more often it is returned. For example, with <code>delayed-retry-min=30000</code> and <code>delayed-retry-max=120000</code>:</p>
<ul>
<li class="">1st return: 30s delay</li>
<li class="">2nd return: 60s delay</li>
<li class="">3rd return: 90s delay</li>
<li class="">4th return and beyond: 120s delay (capped at max)</li>
</ul>
<p>Consumers can also dynamically override this delay on a <strong>per-message</strong> basis. Using AMQP 1.0, a consumer can return a message with the <code>x-opt-delivery-time</code> annotation (a Unix timestamp in milliseconds) in the <a class="" href="https://docs.oasis-open.org/amqp/core/v1.0/os/amqp-core-messaging-v1.0-os.html#type-modified" rel="noopener noreferrer" target="_blank">modified outcome</a>.
This explicit instruction overrides the calculated linear back-off, allowing exact control over redelivery timing.</p>
<p>Defining the delayed retry per-message is useful for entity-specific rate limits.
Imagine your consumer updates records in a third-party SaaS platform.
If the API rejects an update for Tenant A with an HTTP 429 (perhaps they hit their specific tier limit) and a <code>Retry-After</code> header, you don't want to pause your entire consumer and block updates for Tenants B and C.
Instead, your consumer can parse that header and set <code>x-opt-delivery-time</code> just for Tenant A's message.
This ensures the message is redelivered precisely when the API is ready for that specific tenant, while the rest of your system processes normally.</p>
<h4 class="anchor anchorTargetStickyNavbar_Vzrq" id="unlimited-returns">Support for Unlimited Returns<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#unlimited-returns" title="Direct link to Support for Unlimited Returns">​</a></h4>
<p>Up to RabbitMQ 4.2, every requeued message incremented its <code>delivery-count</code> by 1, regardless of the reason.
<a class="" href="https://www.rabbitmq.com/docs/quorum-queues#poison-message-handling">Poison message handling</a> would dead-letter the message once this count exceeded the queue's <code>delivery-limit</code> (default: 20).</p>
<p>Starting with RabbitMQ 4.3, quorum queues track two distinct counters: <code>acquired-count</code> and <code>delivery-count</code>.</p>
<ul>
<li class=""><code>acquired-count</code> increments <em>every time</em> a message is requeued.</li>
<li class=""><code>delivery-count</code> only increments when a message is requeued due to a <strong>failed</strong> delivery attempt.</li>
</ul>
<p>Because poison message handling is still tied to the <code>delivery-count</code>, messages returned <em>without</em> marking the attempt as a failure no longer count toward the limit.
In short, RabbitMQ 4.3 now supports unlimited returns.</p>
<p>By definition, <code>acquired-count</code> will always be greater than or equal to <code>delivery-count</code>. The table below outlines what constitutes a failed delivery:</p>
<table><thead><tr><th style="text-align: left;">Trigger</th><th style="text-align: center;"><code>acquired-count</code> increments</th><th style="text-align: center;"><code>delivery-count</code> increments (delivery attempt <em>failed</em>)</th></tr></thead><tbody><tr><td style="text-align: left;"><strong>AMQP 1.0 <code>released</code></strong> disposition</td><td style="text-align: center;">✅</td><td style="text-align: center;">❌</td></tr><tr><td style="text-align: left;"><strong>AMQP 1.0 <code>rejected</code></strong> disposition</td><td style="text-align: center;">✅</td><td style="text-align: center;">✅</td></tr><tr><td style="text-align: left;"><strong>AMQP 1.0 <code>modified</code></strong> disposition with <code>delivery-failed=false</code></td><td style="text-align: center;">✅</td><td style="text-align: center;">❌</td></tr><tr><td style="text-align: left;"><strong>AMQP 1.0 <code>modified</code></strong> disposition with <code>delivery-failed=true</code></td><td style="text-align: center;">✅</td><td style="text-align: center;">✅</td></tr><tr><td style="text-align: left;"><strong>AMQP 0.9.1 <code>basic.nack</code></strong></td><td style="text-align: center;">✅</td><td style="text-align: center;">❌</td></tr><tr><td style="text-align: left;"><strong>AMQP 0.9.1 <code>basic.reject</code></strong></td><td style="text-align: center;">✅</td><td style="text-align: center;">✅</td></tr><tr><td style="text-align: left;"><strong>Client crash / Connection loss</strong></td><td style="text-align: center;">✅</td><td style="text-align: center;">✅</td></tr><tr><td style="text-align: left;"><strong>Intra-cluster network partition</strong> (consumer node suspected down)</td><td style="text-align: center;">✅</td><td style="text-align: center;">❌</td></tr><tr><td style="text-align: left;"><strong>Consumer timeout</strong> (consumer doesn't acknowledge in time)</td><td style="text-align: center;">✅</td><td style="text-align: center;">❌</td></tr></tbody></table>
<h4 class="anchor anchorTargetStickyNavbar_Vzrq" id="consumer-timeouts">Consumer Timeouts<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#consumer-timeouts" title="Direct link to Consumer Timeouts">​</a></h4>
<p>Consumer timeouts (also known as "message locks") protect against slow or stuck consumers by limiting how long they can hold unacknowledged messages before the broker intervenes.</p>
<p>Historically, timeouts were evaluated globally across all queue types, and a timeout triggered a disruptive AMQP 0.9.1 channel closure. This abruptly terminated <em>all</em> consumers on the channel, not just the stuck one.</p>
<p>In RabbitMQ 4.3, timeout handling has been shifted directly into quorum queues and the new <a class="" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#jms-queue-type">JMS queues</a>. Because <a class="" href="https://www.rabbitmq.com/docs/classic-queues">classic queues</a> and <a class="" href="https://www.rabbitmq.com/docs/streams">streams</a> rarely require this feature, they no longer evaluate consumer timeouts.</p>
<p>When a consumer timeout occurs on a quorum queue, the timed-out messages are returned to the queue (making them available for redelivery), and the server notifies the client using a more graceful, protocol-specific mechanism:</p>
<ul>
<li class=""><strong>AMQP 1.0:</strong> Timed-out messages are released via <code>DISPOSITION(state=released)</code> instead of detaching the link. This allows the consumer to recover without needing to re-attach.</li>
<li class=""><strong>AMQP 0.9.1:</strong> If the client supports the <code>consumer_cancel_notify</code> capability (which most modern clients do), the server sends a <code>basic.cancel</code> notification to cancel <em>only</em> the timed-out consumer, leaving the channel and other consumers intact. If the client lacks this capability, the server falls back to closing the channel to maintain backwards compatibility.</li>
</ul>
<p>Consumer timeouts can be configured in milliseconds at four levels (in order of precedence):</p>
<ol>
<li class=""><strong>Consumer Argument:</strong> <code>x-consumer-timeout</code> (at consumer creation).</li>
<li class=""><strong>Queue Argument:</strong> <code>x-consumer-timeout</code> (at queue declaration).</li>
<li class=""><strong>Queue Policy:</strong> <code>consumer-timeout</code> key.</li>
<li class=""><strong>Global Configuration:</strong> <code>consumer_timeout</code> in <code>rabbitmq.conf</code> (defaults to 1800000 ms, or 30 minutes).</li>
</ol>

<h4 class="anchor anchorTargetStickyNavbar_Vzrq" id="memory-reduction">Memory Usage Reduced by 50%<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#memory-reduction" title="Direct link to Memory Usage Reduced by 50%">​</a></h4>
<p>The per-message memory overhead has been halved for messages that are up to 32 KiB in size, significantly reducing the overall memory footprint of quorum queues.</p>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="khepri">Khepri<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#khepri" title="Direct link to Khepri">​</a></h3>
<p>RabbitMQ metadata includes the definitions of queues, <a class="" href="https://www.rabbitmq.com/docs/exchanges">exchanges</a>, <a class="" href="https://www.rabbitmq.com/docs/exchanges#what-are-bindings">bindings</a>, <a class="" href="https://www.rabbitmq.com/docs/vhosts">vhosts</a>, users, and permissions.
Historically, this data was stored in <a class="" href="https://www.erlang.org/doc/apps/mnesia/mnesia.html" rel="noopener noreferrer" target="_blank">Mnesia</a>, Erlang/OTP's built-in distributed key-value database.</p>
<p>However, Mnesia has two main drawbacks:</p>
<ol>
<li class="">It is prone to inconsistencies during network partitions.</li>
<li class="">It suffers from slow performance under heavy concurrent operations because transactions requiring the same database lock face artificial delays.</li>
</ol>
<p>To solve this, the RabbitMQ team developed <a class="" href="https://rabbitmq.github.io/khepri" rel="noopener noreferrer" target="_blank">Khepri</a>, an open-source distributed database built on Raft.
Khepri guarantees consistency during network faults and delivers superior performance under concurrent client operations by executing transactions serially without database locks.</p>
<p>After experimental support in 3.13 and becoming the default for new clusters in 4.2, <strong>Khepri is now the only supported metadata store in RabbitMQ 4.3.</strong>
Mnesia — along with partition handling strategies like <code>pause_if_all_down</code>, <code>pause_minority</code>, and <code>autoheal</code> — has been entirely removed.</p>

<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="amqp-10-improvements">AMQP 1.0 Improvements<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#amqp-10-improvements" title="Direct link to AMQP 1.0 Improvements">​</a></h3>
<p>Following the introduction of <a class="" href="https://www.rabbitmq.com/blog/2024/08/05/native-amqp" rel="noopener noreferrer" target="_blank">native AMQP 1.0 support</a> in 4.0, <a class="" href="https://www.rabbitmq.com/blog/2025/04/16/amqp-websocket" rel="noopener noreferrer" target="_blank">AMQP 1.0 over WebSocket</a> and <a class="" href="https://www.rabbitmq.com/blog/2024/12/13/amqp-filter-expressions" rel="noopener noreferrer" target="_blank">Filter Expressions</a> in 4.1, as well as <a class="" href="https://www.rabbitmq.com/blog/2025/09/23/sql-filter-expressions" rel="noopener noreferrer" target="_blank">SQL Filter Expressions</a> in 4.2, RabbitMQ 4.3 brings two more <a class="" href="https://www.rabbitmq.com/docs/amqp">AMQP 1.0</a> enhancements.</p>
<h4 class="anchor anchorTargetStickyNavbar_Vzrq" id="amqp-rejection-reason">Rejected-by &amp; Rejection Reason<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#amqp-rejection-reason" title="Direct link to Rejected-by &amp; Rejection Reason">​</a></h4>
<p>When a queue rejects a message, RabbitMQ now passes the queue name and the specific rejection reason (e.g., maximum length reached, queue unavailable) back to the AMQP 1.0 publisher in the <a class="" href="https://docs.oasis-open.org/amqp/core/v1.0/os/amqp-core-messaging-v1.0-os.html#type-rejected" rel="noopener noreferrer" target="_blank">Rejected outcome</a>. This is useful when multiple queues are bound to a single exchange, allowing publishers to pinpoint exactly which queue failed and why.</p>
<h4 class="anchor anchorTargetStickyNavbar_Vzrq" id="consumer-activity-notification">Consumer Activity Notification<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#consumer-activity-notification" title="Direct link to Consumer Activity Notification">​</a></h4>
<p>RabbitMQ now signals link state information to consumers via AMQP 1.0 <a class="" href="https://docs.oasis-open.org/amqp/core/v1.0/os/amqp-core-transport-v1.0-os.html#type-flow" rel="noopener noreferrer" target="_blank">flow frame</a> properties. When consuming from a quorum queue with <a class="" href="https://www.rabbitmq.com/docs/consumers#single-active-consumer">Single Active Consumer</a> enabled, RabbitMQ will notify the consumer immediately upon transitioning from an inactive (waiting) state to an active state, and vice versa.</p>

<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="jms-queue-type">JMS Queue Type<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#jms-queue-type" title="Direct link to JMS Queue Type">​</a></h3>
<p>VMware Tanzu RabbitMQ 4.3 introduces a purpose-built queue type for <a class="" href="https://jakarta.ee/specifications/messaging/3.1/jakarta-messaging-spec-3.1" rel="noopener noreferrer" target="_blank">JMS (Java Message Service)</a> applications.
Backed by Raft, the new <a class="" href="https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-rabbitmq-oci/4-3/tanzu-rabbitmq-oci-image/site-jms.html" rel="noopener noreferrer" target="_blank">JMS queue type</a> provides the same safety guarantees as Quorum Queues: messages and their delivery states are replicated across nodes, ensuring durability and consistency even during network failures.</p>
<p>This architecture offers a massive advantage over legacy JMS brokers, which typically rely on shared storage (SAN/NAS) or fragile active/passive failovers susceptible to split-brain scenarios and data loss.</p>
<p>While optimized for the <a class="" href="https://github.com/apache/qpid-jms" rel="noopener noreferrer" target="_blank">Qpid JMS client</a> over AMQP 1.0, this queue is cross-protocol by design.
A consumer could be a JMS application, while the publisher could be a non-Java client operating over AMQP 1.0, AMQP 0.9.1, STOMP, or MQTT.</p>

<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="apache-spark-connector">Apache Spark Connector<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#apache-spark-connector" title="Direct link to Apache Spark Connector">​</a></h3>
<p><a class="" href="https://spark.apache.org/" rel="noopener noreferrer" target="_blank">Apache Spark</a> is a popular open source project for large-scale data analytics and machine learning workloads.</p>
<p>VMware Tanzu RabbitMQ 4.3 ships a new <a class="" href="https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-rmq-apache-spark/1-0/rmq-apache-spark-connector/overview.html" rel="noopener noreferrer" target="_blank">RabbitMQ Stream Connector for Apache Spark</a> providing high-speed, parallel data transfer between <a class="" href="https://www.rabbitmq.com/docs/streams">RabbitMQ Streams</a> and an Apache Spark cluster.
It bridges the gap between high-throughput messaging and big data processing.
By combining them, you get a powerful, end-to-end pipeline where RabbitMQ acts as the reliable, high-speed ingestion layer (the "nervous system") and Spark acts as the distributed computing engine (the "brain").</p>
<p>This unlocks advanced, enterprise-scale use cases:</p>
<ul>
<li class=""><strong>Unified Batch and Stream Processing:</strong> Because Streams store data durably and support arbitrary offset replay, the exact same Structured Streaming code can process historical batches and live data.</li>
<li class=""><strong>Real-time Machine Learning (MLlib):</strong> Train models on historical data and apply them to live streams for instant fraud detection or dynamic pricing.</li>
<li class=""><strong>Complex Windowed Aggregations:</strong> Execute time-windowed Spark SQL queries (e.g., "5-minute rolling temperature averages") directly against live RabbitMQ streams.</li>
<li class=""><strong>On-the-Fly Enrichment:</strong> Join fast-moving event streams with static database tables before sinking the enriched data.</li>
<li class=""><strong>Data Archival:</strong> Batch historical stream data into long-term cold storage or data lakes.</li>
</ul>
<p>Key features:</p>
<ul>
<li class=""><strong><a class="" href="https://www.rabbitmq.com/docs/streams#super-streams">Super Stream</a> Support:</strong> Scales seamlessly from individual streams to partitioned Super Streams.</li>
<li class=""><strong>Flexible Offsets:</strong> Start reading from the absolute beginning, the current tail, a specific offset, or a timestamp.</li>
<li class=""><strong>Optimized Field Extraction:</strong> Pull only the required fields to minimize memory consumption.</li>
<li class=""><strong>Built-in Rate Limiting:</strong> Cap records per trigger interval for predictable performance.</li>
<li class=""><strong>Full AMQP Access:</strong> Read payloads, properties, and temporal fields simultaneously.</li>
<li class=""><strong>Deterministic Partitioning:</strong> Hash-based partitioning for writing Spark data back to RabbitMQ Streams.</li>
</ul>

<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="stream-browser">Stream Browser<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#stream-browser" title="Direct link to Stream Browser">​</a></h3>
<p>The <a class="" href="https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-rabbitmq-oci/4-3/tanzu-rabbitmq-oci-image/site-stream-browser.html" rel="noopener noreferrer" target="_blank">Stream Browser</a> is a new Management UI plugin offering direct visibility into your stream contents. Found under the <strong>Stream Browser</strong> tab, it provides:</p>
<ul>
<li class=""><strong>Unified Search:</strong> Instantly locate streams and super-streams.</li>
<li class=""><strong>Flexible Navigation:</strong> Start browsing by absolute offset, timestamp, or from the head/tail.</li>
<li class=""><strong>Deep Inspection:</strong> View data in tabular format or expand individual messages to see all AMQP 1.0 sections.</li>
<li class=""><strong>Structural Views:</strong> Navigate by physical segment files and chunks to understand low-level disk layout.</li>

<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="message-scheduler">Message Scheduler<a class="hash-link" href="https://www.rabbitmq.com/blog/2026/04/23/rabbitmq-4.3-release#message-scheduler" title="Direct link to Message Scheduler">​</a></h3>
<p>A message scheduler allows producers to target a specific future delivery time.
The broker holds the message outside the target queue(s) until the delay expires, at which point it internally publishes the message.</p>
<p>This "publish at time T" paradigm is perfect for:</p>
<ul>
<li class=""><strong>Business workflows:</strong> "Send an abandoned cart email in 2 hours."</li>
<li class=""><strong>Temporal decoupling:</strong> Ensuring events aren't processed prematurely.</li>
<li class=""><strong>Fan-out:</strong> Routing a single delayed message to multiple queues (e.g., send a message later to any online subscriber).</li>
</ul>

Due to severe architectural limitations, that plugin has been deprecated and archived.</p></div></div>
<p>VMware Tanzu RabbitMQ 4.3 replaces it entirely with a new, enterprise-grade <a class="" href="https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-rabbitmq-oci/4-3/tanzu-rabbitmq-oci-image/site-delayed-queues.html" rel="noopener noreferrer" target="_blank">Delayed Queue</a> plugin:</p>
<ul>
<li class=""><strong>High Availability:</strong> Fully backed by Raft replication.</li>
<li class=""><strong>Standard Protocols:</strong> Uses standard AMQP 1.0 annotations (<code>x-opt-delivery-time</code>, <code>x-opt-delivery-delay</code>) for absolute and relative delays.</li>
<li class=""><strong>Pub/Sub Integration:</strong> Seamlessly works with exchanges (e.g., <code>topic</code>), ensuring one delayed message can route to many MQTT or JMS subscriptions.</li>

</ul>
